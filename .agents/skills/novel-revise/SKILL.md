# 小说设定修订

让用户作为作者主动修改故事，帮助其看清取舍并把选择落实到本地 Markdown。既有大纲与人物档案可以被用户修订，不以“人设已固定”为由拒绝。默认一工程一本小说，自动读取材料，不要求选书或复述剧情。

## 1. 读取与定位

读取工程及小说局部 AGENTS.md，自动定位根目录或 novels/<slug>/ 的小说，沿用现有结构。读取 index.md、novel.md、design.md、revisions/index.md（若存在）、大纲与最新实际正文。

根据请求读取目标故事线、人物 profile、goals、state、关系、知识与相关记忆，并以人物 ID、事件 ID、关键词和来源检索受影响旧章、伏笔、回报及专属梗。参考 [影响分析与同步](references/impact-and-sync.md)。不要只改一份 profile 就认为已完成。

无小说材料时说明现状，引导先初始化，不生成任意小说。确有多个有效内容根且无法定位时才澄清路径。

## 2. 和用户探索改法

用户只表达模糊想法时，简要说明现有设计与矛盾，提出具体改法及取舍，每轮只问 1–3 个关键问题。讨论“更冷酷”“更聪明”等标签时，转成具体行为：如何排序价值、面对何种压力、愿意付出什么、哪些人或事构成例外、底线和弱点是什么。

主线调整讨论主角目标、对立力量、因果转折、关系变化及主题是否改变，同时评估阅读承诺与旧伏笔的去向。用户已有明确方案时直接沿用，不重复让其选择。

区分三种修订方式：

- **补充或澄清**：填补未说明的性格、背景或动机，不否认已写事实。
- **从某时点发展**：此前性格与经历保留，后续通过压力、选择和事件逐步变化；计划中的成长不提前变成当前事实。
- **追溯改设定**：作者认定旧设定应改，检查并修订与之冲突的已有内容；不虚构一场人物“突然成长”来掩饰作者修订。

默认在不矛盾前提下补充、修改未来计划；若不同修订方式会改变已写正文且用户未表达选择，询问具体范围。不要默默决定全书重写。用户已明确要求追溯修改或同步相关章节时，按授权执行，不再追加泛泛批准。

用户仅说“讨论”时留在讨论，不改有效档案。说“按这个改”“补充为……”或已给明确更新要求时，直接完成文件更新；未决项可记录为暂定，不能伪装成用户决定。

## 3. 形成可执行修订

用简洁对照说明修改前后、原因、故事生效时间或范围、主要连带影响。小修改不必输出庞大计划；复杂改动按依赖整理，先让核心设计自洽。

执行前创建本次 `revisions/rev-NNN.md`，记录用户要求、采用方案、适用方式、修改范围、待处理项以及相关文件修改前的关键片段。用 `revisions/index.md` 登记，并链接进小说 index。路径按小说根计算，ID 在本书唯一。

不创建空的章节正文来凑修订范围。计划、正式事实和人物视角保持分开；作者允许修改设计不代表允许自动将草稿定稿。

## 4. 更新本地档案

按照影响参考执行最小必要修改，保留用户无关文字和稳定 ID。每个文件先读再改；检查工作区已有改动，避免误覆盖。对引用使用相对路径与可检索正文定位。

人物变化更新 profile 中的行为依据、例外和适用时间，并按需维护 personality-history.md；目标、情绪、知识和记忆分别更新，不因更改一个标签凭空改变所有经历。追溯改设定保留作者修订来源，故事内成长必须有相应正文事件。

主线变化同步相关卷、故事线、章节计划、回报条件、伏笔和专属梗。涉及实际正文的修改按已授权范围处理，再同步事实和人物认知。推演记录保留为历史，标记哪些结果已失效，不重写成从未发生过的执行记录。

用户明确保留旧章时，选择能兼容旧章的解释或未来发展路径。确有不能兼容的冲突则列出待修章节与具体原因，并标明修订尚未全量一致，不能通过静默改写旧章解决。

## 5. 检查并交付

检查新旧设定的适用时间、因果链、人物知情范围、稳定 ID、链接与素材依赖。完整检索受影响的旧说法，区分应保留的历史与应修正的当前描述，不做全局字符串替换。

在修订记录逐项标记 applied、pending 或 not-needed，整体状态区分 applied（授权范围内且无相关未解决冲突）、partial、proposed。中断后按当前文件与记录恢复，不重复追加同一变更。

最终给出变更要点、实际修改文件、影响范围和未解决项。不得将局部更新宣称为全书已一致。此 Skill 不默认调用人物 Sub Agent；后续需要用新档案推演章节时进入 novel-continue。
